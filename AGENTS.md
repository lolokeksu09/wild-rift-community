# Инструкции для ИИ и разработчиков

Проект — отдельное сообщество Wild Rift, не RiftCore. Название не выбрано. Начинать с PROJECT_STATE.md, docs/WORKFLOW.md и текущей задачи; далее читать только релевантные документы и код.

1. Не выдавать планы, макеты, локальные данные и заглушки за реализованные серверные функции.
2. Сохранять архитектуру и имена. Делать минимальные связанные изменения по задаче.
3. Не выдумывать API Riot, игровые данные, URL, ветки, remotes и доступы. Сначала проверить официальный поддерживаемый механизм.
4. Любое действие с приватным контентом проверять на сервере. Учитывать поиск, файлы, кеш, real-time и уведомления.
5. Не хранить секреты в коде или логах. Не отправлять сообщения людям без явного поручения владельца.
6. Для миграций, удаления и других разрушительных действий объяснить последствия и план восстановления до выполнения.
7. Не публиковать сервис и не включать платные услуги без соответствующего поручения. Не добавлять необоснованные запросы подтверждения для обычной обратимой работы.
8. Тестировать риски: чужой доступ, повтор запроса, параллельное занятие последнего места, отзыв членства, потеря соединения.
9. Перед завершением сообщить: что сделано, что проверено, ограничения, следующий шаг. Не заявлять о проверках, которые не выполнялись.
10. Обновлять документы, если изменились договорённости, маршруты или поведение.
11. Русский язык пользовательского интерфейса — текущая проектная настройка. Интерфейс не показывает служебную терминологию без необходимости.
12. Не подключать новые зависимости и службы только ради масштаба. Сначала обосновать их задачей.

## Рабочий цикл

Установить цель и критерии приёмки → прочитать актуальный код → реализовать → проверить существенные риски → обновить документы → представить результат. Если входных данных не хватает, выполнить доступную часть и задать один конкретный вопрос. Правила проекта не отменяют ограничения среды и инструкции более высокого уровня.

## Текущая веб-версия

Рабочий продукт — сайт на Node.js 24.19, SQLite, Docker и Caddy. Текущая версия схемы — 25; установленную схему уточнять по PROJECT_STATE.md. Карта документов — docs/README.md; ТЗ, архитектуру и дорожную карту читать по необходимости.

Утверждённый дизайн — этап 24: docs/DESIGN_BASELINE_STAGE24.md и docs/WEB_REDESIGN_PLAN.md. Новые изменения дизайна — с этапа 25. Сохранять server/public, миграции, fixtures и пользовательские данные. Публикация кода и боевое развёртывание — отдельные действия; VDS Deploy только по команде владельца.

Следовать матрице проверок в docs/WORKFLOW.md: локально проверять затронутые риски, один полный npm run verify перед функциональным выпуском; Docker и полный браузерный набор преимущественно в GitHub Actions. Для документационных изменений достаточно npm run check:docs и git diff --check. npm run check:docs проверяет локальные Markdown-ссылки; внешние URL и якоря проверяются отдельно.

## Экономия времени и контекста

Один коммит на готовый этап; промежуточные запуски только при необходимости. Использовать API, точечные чтения через rg, краткие логи ошибок; не перечитывать историю и не повторять успешные проверки без причины. Не снижать проверки миграций, доступа и сохранности данных ради экономии. Основная поставка — готовый ZIP и точная команда Termux. Документационные изменения — без ZIP и deploy.

Обязательно применять договорённость об ускорении из docs/WORKFLOW.md: небольшие правки — одно дерево GitHub; большие файлы — blobs с проверкой SHA; удалённое дерево сверять с локальным. Переиспользовать сборщик ZIP и шаблон установщика; инструменты закреплены в tools/build-release.py и tools/prepare-github-tree.py; команды и ограничения — в docs/WORKFLOW.md.

Номер схемы менять точечно в проверках схемы. Не заменять числа глобально: счётчики демо-ботов, аккаунтов и другие константы независимы. Изменения deploy/smoke-image.sh проверять через server/tests/deploy-smoke.test.mjs; этот тест исполняет фактическое выражение smoke-проверки на холодной копии. Docker-ограничения отдельно проверяются в Actions и при установке.
