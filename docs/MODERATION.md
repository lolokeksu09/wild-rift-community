# Жалобы на сообщения · 0.7

В чате клуба и принятой личной беседе у чужих сообщений есть кнопка «Пожаловаться». Перед отправкой интерфейс сообщает: модератор получит текст выбранного сообщения и пояснение. Сервер копирует текст самостоятельно; подменить его в запросе нельзя. Одна жалоба от пользователя на сообщение; повтор возвращает прежний ID, новое пояснение не перезаписывает старое.

Раздел «Жалобы» показывает последние 100 собственных обращений и публичное объяснение решения. Модератор сервиса дополнительно получает очередь по 50 записей с догрузкой. Доступа ко всей личной беседе назначение не даёт. Рассматривать свою жалобу или жалобу на себя нельзя. Решения: «Нарушение подтверждено» / «Отклонено». Повтор решения идемпотентен; конфликт отклоняется. Решение записывается вместе с модератором, временем и объяснением в moderation_audit. HTTP-редактирования журнала нет; владелец файла SQLite технически может изменить базу.

Подтверждение нарушения пока не удаляет сообщение и не блокирует автора: санкции, апелляции и жалобы на другие виды контента остаются отдельными задачами; уведомления о решениях добавлены в 0.8. В журнале пока фиксируются решения, не чтения жалоб. Визуальная проверка очереди в браузере ещё не выполнена.

## Назначение модератора локального сервера

Роль выдаёт оператор сервера через переменную окружения COMMUNITY_MODERATOR_IDS — список точных ID существующих аккаунтов через запятую. ID текущего аккаунта доступен в авторизованном GET /api/me (user.id). Список считывается при запуске, изменение и отзыв требуют перезапуска. По умолчанию модераторов нет. Регистрация и редактирование профиля роль не меняют. В этой поставке реальные аккаунты модераторами не назначались.

## API

- POST /api/reports: {kind: direct|club, messageId: integer, reason: string}, причина 3–1000 символов.
- GET /api/reports: только свои статусы и объяснения, без ID других участников.
- GET /api/moderation/reports?before=ID: очередь модератора, включая снимок только выбранного сообщения.
- POST /api/moderation/reports/:id/decision: {decision: upheld|dismissed, note: string}.

Все маршруты требуют сеанс, изменения — существующую CSRF/Origin-защиту. В клубе жаловаться может только действующий участник. В личной беседе — участник, в том числе после блокировки или отклонения запроса, чтобы блокировка не мешала сообщить о нарушении. API поддерживает жалобу на первое сообщение запроса, кнопка на карточке запроса добавлена в 0.8. Текст возвращается только модераторской очереди; право подачи жалобы не открывает историю заблокированной беседы.

## Данные и обновление

Миграция 4→5 транзакционно добавляет reports и moderation_audit. Существующие данные не удаляются. Жалоба сохраняет отдельную копию сообщения; политику срока хранения необходимо определить до публичного запуска. Перед обновлением остановить сервер и скопировать каталог data целиком. Для отката восстановить копию и предыдущую версию приложения; не понижать user_version вручную.

## Проверки

37 серверных тестов прошли: чужой доступ, запрет самоназначения, параллельные повторы, граница приватного контекста, запрет собственной модерации, повтор/конфликт решения, единственная запись аудита, отзыв роли и сохранение решения после перезапуска. DOM-наборы server-ui, direct-ui, chat-ui прошли; chat-ui дополнительно отправляет жалобу на реальный сервер. Эти проверки не являются визуальной проверкой браузера или нагрузочным тестом. Сервис остаётся локальным.

## Завершение сценария обращения · 0.8

На карточке входящего запроса (в том числе отклонённого) появилась кнопка жалобы на первое сообщение. Она не принимает запрос и не открывает переписку. Перед отправкой пользователь видит, что модератору будет передан текст сообщения и пояснение.

Навигация «Жалобы» показывает количество новых решений, обновляясь раз в 5 секунд. Это внутреннее уведомление, без push. Список собственных обращений теперь имеет догрузку по 100 записей. Решение помечается прочитанным явно, отдельной кнопкой; простой просмотр списка статус не меняет. Отметка сохраняется на сервере между сеансами. Собеседник и модератор не могут отметить решение вместо заявителя.

Новые API:
- GET /api/reports/summary — {viewerId, unread}, только собственные новые решения, без текста и чужих ID.
- POST /api/reports/:id/read — отметить собственное принятое решение прочитанным; повтор безопасен. До решения — 409, чужое обращение — 404.
- GET /api/reports?before=ID — следующая страница собственных обращений; next в ответе.

Схема 5→6 добавляет reports.decision_seen. Старые решения первоначально считаются непрочитанными; жалобы, сообщения и журнал не изменяются. Перед запуском остановить сервер и скопировать каталог базы. Откат — восстановление копии с предыдущей версией приложения.

Проверки 0.8: 38 серверных тестов PASS, четыре DOM-набора PASS. Новый test:moderation-ui проходит весь сценарий через HTTP/SQLite: жалоба из непринятого запроса, решение в интерфейсе отдельного модератора, индикатор заявителя, отметка прочтения. Проверяет сохранение pending у запроса и экранирование текста сообщения/решения. Визуальную проверку браузером DOM не заменяет.

Остаются: санкции, апелляции, общая система уведомлений, сроки хранения снимков и аудит чтения жалоб.
