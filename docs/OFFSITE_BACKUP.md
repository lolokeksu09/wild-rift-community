# Зашифрованные внешние копии · 0.24

Код подготовлен; внешнее хранилище и расписание ещё не подключены. Само наличие этих инструментов не означает, что копии уже уходят с VDS. Каталог назначения должен находиться на другом сервере/диске с независимым доступом. Не использовать GitHub artifacts или репозиторий для базы игроков.

## Снимок и проверка

server/backup-cli.mjs использует встроенный [SQLite backup API Node.js](https://nodejs.org/download/release/v24.19.0/docs/api/sqlite.html#sqlitebackupsource-db-path-options) для согласованного снимка работающей WAL-базы. Исходник открывается read-only и не мигрируется. Снимок проходит integrity_check, foreign_key_check и проверку схемы 19, затем шифруется потоком AES-256-GCM. Формат WRBACK01: заголовок и случайный nonce, зашифрованная SQLite, тег аутентичности. Новых зависимостей нет. Временный незашифрованный снимок находится в закрытом каталоге и очищается при обычном завершении, включая ошибки; аварийное отключение процесса может оставить временный каталог — проверять его при обслуживании. На Windows права каталога определяются также ACL пользователя.

Ключ WR_BACKUP_KEY — 32 случайных байта, записанные как 64 hex-символа. Хранить в защищённом файле конфигурации и отдельном безопасном месте вне VDS и вне репозитория. Без ключа копия невосстановима. Передавать через окружение, не аргумент командной строки; не печатать и не включать set -x.

Команды (ключ уже находится в окружении):

```sh
node server/backup-cli.mjs create /path/community.sqlite /private/new-copy.wrbackup
node server/backup-cli.mjs restore /private/new-copy.wrbackup /isolated/new-community.sqlite
```

Файл назначения должен отсутствовать. Создание отказывается перезаписывать копию; восстановление проверяет GCM и SQLite перед публикацией файла и никогда не заменяет существующую базу. Перед восстановлением рабочей базы нужны отдельный план остановки/возврата и оценка потери поздних изменений. Проверка выполняется на отдельном файле.

Восстановленный снимок сохраняет аккаунты/контент/изображения, но удаляет сеансы и резервные коды, чтобы старые cookie и использованные коды не ожили. Пароль возвращается к дате снимка. Файл архива и исходная база не меняются.

## Перенос на независимый SSH-сервер

deploy/offsite-backup.sh запускается оператором на VDS из /opt/wild-rift-community. Он берёт закрытую конфигурацию из окружения:

- WR_BACKUP_KEY — ключ шифрования.
- WR_BACKUP_TARGET — фактический user@host:/absolute/directory; каталог уже создан с ограниченными правами на независимом сервере.
- WR_BACKUP_SSH_KEY_FILE — отдельный ключ для резервирования с минимальными правами.
- WR_BACKUP_KNOWN_HOSTS — файл с проверенным и закреплённым ключом хоста назначения.

Скрипт получает блокировку flock, создаёт снимок внутри приложения, выносит только ciphertext через docker cp, передаёт scp с BatchMode/StrictHostKeyChecking, скачивает файл обратно, сравнивает байты и восстанавливает его в отдельном контейнере без сети. Только после этого сообщает «External backup verified». Команда завершается ошибкой при отказе любого шага. Подмена хоста, неверный ключ или повреждение архива не обходятся. Требуется root-оператор, Docker Compose, SSH/scp, flock и openssl на VDS. Все временные имена создаются скриптом; файлы рабочей базы не удаляются.

Автоматическое удаление старых внешних копий отсутствует. Ротация, квота, частота, допустимая потеря данных и уведомления о сбое должны быть выбраны до активации расписания. Конфигурацию, ключи и саму копию сюда не добавлять. Расписание не активируется автоматически при выпуске.

## Граница проверки

server/tests/encrypted-backup.test.mjs проверяет снимок открытой WAL-базы, сохранность приватного содержимого/пароля, независимую запись после восстановления, отзыв сеансов/кодов, отказ от перезаписи, повреждение и неверный ключ. Это локальная тренировка: до подтверждённого запуска offsite-backup.sh на фактическом внешнем сервере нельзя заявлять о работающем внешнем резервировании.
