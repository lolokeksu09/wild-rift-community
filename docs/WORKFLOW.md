# Работа с минимальными затратами времени и контекста

## Начало задачи

1. Читать `AGENTS.md`, `PROJECT_STATE.md` и текущую задачу.
2. Проверить состояние рабочей копии; затем найти нужные функции через `rg` и прочитать конкретные участки. Не выводить целиком большие файлы, каталоги зависимостей и реестры инструментов.
3. Использовать тематические документы из карты документации. Всё ТЗ, архитектуру и историю читать только при изменении соответствующих договорённостей или отсутствии нужного контекста.
4. Продолжать существующую работу. Сохранять рабочие изменения и чужие коммиты. Уточнять только то, что влияет на реализацию и не следует из контекста.

## Проверки

| Изменение | Локально | GitHub Actions |
| --- | --- | --- |
| Только документация | `npm run check:docs`, `git diff --check` | Проверка ссылок; без установки зависимостей, Docker и браузера |
| Серверная функция | Тесты затронутого модуля и существенных рисков | Полный `npm run verify`, Docker и браузерные сценарии |
| UI и стили | Затронутый DOM-сценарий; доступная браузерная проверка нужных экранов | Полный набор, снимки интерфейса |
| SQLite, права доступа, резервирование, установка | Проверки миграции, сохранности данных, прав, повторов и восстановления | Полный набор и проверка контейнера на холодной копии |

Перед готовым функциональным выпуском выполнять один полный `npm run verify` локально, если это доступно. Не повторять весь набор после чисто документационных изменений; новую проверку запускать после исправления ошибки или изменения поведения. Перед упаковкой должны быть известны результаты необходимых проверок. Не выдавать DOM-тесты за визуальную проверку, а запущенный CI — за успешный.

Тяжёлые Docker- и полные браузерные проверки выполняются преимущественно в Actions. Локальный браузер использовать для воспроизведения конкретного дефекта и просмотра затронутого экрана. При недоступности браузера прямо указать ограничение; не отключать защиту среды ради теста.

## GitHub

- Один коммит на готовый этап с исходниками, необходимыми тестами и документацией. Дополнительный коммит допустим для реального исправления найденной ошибки. Не публиковать каждый промежуточный шаг ради запуска CI.
- Перед обновлением ветки проверять ожидаемую вершину; при несовпадении изучить чужие изменения. Не перезаписывать историю.
- Предпочитать GitHub API. Браузер — для нужного действия, которого нет в доступном API, например ручного запуска существующего deploy.
- После публикации проверить итог CI. Если готовый архив выдан до завершения CI, явно назвать CI незавершённым; не утверждать готовность к боевой установке без требуемых проверок.
- Не ждать CI частыми вызовами: смотреть статус по завершении другого полезного шага или с интервалом около минуты. Читать логи упавшего шага и конкретные строки ошибок. Успешный запуск достаточно подтвердить итогом; снимки скачивать только когда нужен визуальный результат.
- Нужные промежуточные результаты и идентификаторы сохранять и повторно использовать. Независимые чтения объединять, изменения и обновления веток выполнять последовательно.

## Поставка и deploy

Функциональный выпуск: `wr-community-design-stageN.zip` с исходниками, `RELEASE_SHA`, SHA-256, проверенным `deploy-from-termux.sh` и кратким README. Имя и внутренняя папка должны поддерживаться существующим `wr-deploy-latest.sh`. Архив включает утверждённое оформление и текущие изменения; базы, секреты, зависимости и сборочный мусор не включать.

К архиву сразу приложить точную команду:

```bash
bash "$HOME/wr-deploy/wr-deploy-latest.sh"
```

Установка владельцем через Termux — основной способ обновления. Не ждать его выполнения в рабочем цикле; отметить «установка не подтверждена». Deploy через Actions запускать только по отдельной команде владельца, сохраняя резервирование и проверку HTTPS. `.github/workflows/vds-deploy.yml` не менять.

Документационные изменения публиковать без нового этапа и ZIP. Не запускать deploy для исправления документации.

## Документы и ответы

- `PROJECT_STATE.md` — короткая точка входа: выпуск кода, последняя подтверждённая установка, архив, проверки, ограничения и ближайшая задача. Обновлять при изменении этих фактов. Не писать в него SHA собственного документационного коммита: это создаёт бесконечную цепочку правок.
- Тематический документ — поведение новой функции и ограничения. Исторические отчёты не переписывать под текущий выпуск.
- Ответ: результат, готовый файл/коммит, выполненные проверки, существенное ограничение и один следующий шаг. Не повторять весь контекст.
- Сообщения о ходе работы краткие: новое установленное обстоятельство, проблема либо результат. Не пересказывать каждую команду.

## Ускорение следующих этапов — договорённость 8 октября 2026

- Начинать с короткого состояния и текущей задачи; читать только нужные функции. Не восстанавливать весь контекст проекта перед каждой правкой.
- Маленькие текстовые изменения публиковать одним деревом GitHub с содержимым файлов, без отдельного запроса на каждый blob. Для больших файлов использовать отдельные blobs с проверкой SHA. Перед коммитом сверять SHA удалённого дерева с локальным `git write-tree`, затем обновлять ветку с проверкой ожидаемой вершины.
- Не передавать большой пакет исходников через вывод, который может быть обрезан инструментом. Ограничивать чтение размером доступного ответа; при необходимости читать частями. Не использовать обрезанные данные для публикации.
- Сначала запускать тесты затронутой функции. Один полный `npm run verify` перед готовым функциональным выпуском; повтор после ошибки или изменения поведения обоснован. Для документации — только ссылки и `git diff --check`.
- Docker и полный браузерный набор выполнять преимущественно в Actions. Не опрашивать статус часто. Выдавать архив с фактическим статусом CI; незавершённые или недоступные проверки явно отмечать.
- Переиспользовать проверенный сборщик ZIP и шаблон установщика. Не писать упаковку заново для каждого этапа. Меняются номер этапа, коммит и описание выпуска; `RELEASE_SHA` и контрольные суммы вычисляются автоматически.
- Не обещать фиксированное время или процент экономии без замера. Сокращать лишние чтения, запросы и повторные проверки, сохраняя проверки доступа, миграции и данных.

Уже внедрены: короткий файл состояния, матрица проверок, сокращённый CI для документации и сверка публикуемого дерева с локальным. В этапе 28 также закреплены сборщик ZIP и подготовка публикации одним деревом (команды ниже).

## Инструменты выпуска

Требуются Python 3, Git и Bash. Сборщик использует только стандартную библиотеку Python, экспортирует текущий чистый коммит и не запускает deploy:

```bash
python3 tools/build-release.py --stage 28 --output-dir /workspace/scratch --description docs/RELEASE_STAGE28.md
```

Для следующего этапа менять номер и путь к документу с изменениями и фактическим статусом проверок. Шаблон SSH-установщика — [deploy-from-termux.template.sh](../deploy/deploy-from-termux.template.sh); секретов в нём нет. Сборщик вычисляет `RELEASE_SHA`, SHA-256 исходников и ZIP, создаёт `SHA256SUMS.txt`, проверяет ZIP и синтаксис установщика. Грязная рабочая копия, уже существующий ZIP, приватные и сборочные файлы в коммите отклоняются. Архивы одного коммита и этапа воспроизводимы.

Подготовка только уже staged изменений, без изменения индекса и удалённой ветки:

```bash
python3 tools/prepare-github-tree.py --output /tmp/wr-stage28-github-tree.json
```

План содержит родителя, базовое и ожидаемое дерево, `tree_elements` и при необходимости `blobs`. Небольшие UTF-8 файлы включены в дерево; бинарные и файлы более 64 KiB требуют предварительного `create_blob` и сверки SHA. Использовать доступный GitHub API: создать нужные blobs, затем одно дерево, сверить `tree_sha`, создать коммит и обновить ветку с `expected_sha=parent_sha`. Удаления и режим исполняемых файлов сохраняются. Сам инструмент не делает сетевых запросов и не публикует файлы. Планы с содержимым исходников хранить во временном каталоге, не коммитить.

Проверка инструментов:

```bash
python3 -m unittest discover -s tools/tests
```
