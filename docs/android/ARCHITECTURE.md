# Архитектура Android

Дата 05.10.2026. Целевая архитектура; гостевая основа A01 уже реализована в android/. [Официальные рекомендации Android](https://developer.android.com/topic/architecture/recommendations) служат ориентиром; ниже — решения именно нашего проекта.

## Слои

```text
app/                         запуск, навигация, композиция зависимостей
ui/theme/, ui/components/    тема и общие компоненты
features/auth/, home/, clubs/, messages/, profile/
  экран → ViewModel → UiState и действия
data/api/                   HTTP, DTO, ошибки, cookie/CSRF
data/repository/            операции, преобразование DTO, правила кеша
data/local/                 настройки; черновики/кеш при необходимости
```

Один app-модуль, один Activity и Compose. Composable получает состояние и обработчики, не управляет HTTP. ViewModel владеет сценарием; Repository — загрузкой и записью. Coroutines/Flow используются для асинхронных состояний; подписки привязаны к жизненному циклу. Domain-слой добавляется только для повторяемых сложных сценариев, а не как обязательная прослойка.

На A01 достаточно простой явной композиции зависимостей. DI-фреймворк, многомодульность и дополнительные базы не являются предварительным условием. Стабильные версии HTTP/serialization/navigation/image библиотек выбрать и закрепить при создании сборки.

## Состояние экрана

UiState различает initial-loading, content, empty, error, offline, forbidden. Отдельные признаки refresh/pagination/submit позволяют сохранить содержимое и ввод при повторной загрузке. Одно действие не запускает параллельные дубли отправки; успешная запись отображается после подтверждения API.

При уничтожении Activity восстановить маршрут, фильтр и безопасный ввод. Пароли и секреты не помещать в SavedStateHandle. Draft изображений учитывает утрату доступа к URI. Ошибка пагинации не стирает первую страницу.

## API и приватность

Сервер остаётся владельцем прав: членство, роли, блокировки, лимиты, согласие на переписку. Клиент может скрывать недоступные действия, но это не защита данных. Все запросы через HTTPS с обычной проверкой сертификата; обход TLS ради IP-адреса запрещён.

DTO соответствует фактическому JSON. Внутренняя модель может иметь удобные имена, но snake_case/camelCase преобразуются явно. Пользователи и клубы имеют строковые ID, посты — числовые. Курсоры передаются без пересборки. API пока не имеет обещанного versioned/mobile-контракта: на A01 закрепить конкретные ответы тестами, на A02 проверить транспорт входа.

## Локальное хранение

DataStore — кандидат для небольших настроек; Room — для структурированных черновиков/кеша, когда появляется такой сценарий ([DataStore](https://developer.android.com/topic/libraries/architecture/datastore), [Room](https://developer.android.com/training/data-storage/room)). A01 не требует Room.

Сеанс хранится защищённо; механизм шифрования, Android Keystore и исключения backup определить и проверить на A02. Пароль не сохранять. Аккаунт входит в ключ кеша и владельца очереди. При выходе отменить запросы, удалить сеанс и приватные данные; поздний ответ старого аккаунта не может заполнить новый экран. При 401 закрыть приватные данные; при 403/404 удалить недоступный объект из кеша. Чувствительные изображения не сохранять в общий дисковый кеш.

Начальный релиз требует сеть для записи. Очередь offline не универсальна: появляется лишь для операций с подтверждённым clientId/серверной защитой повторов. Смена аккаунта не отправляет старый draft от нового пользователя.

## Совместимость и выпуск

Версии Gradle/AGP/Kotlin/JDK/Compose фиксируются вместе на A01. minSdk и targetSdk выбираются по устройствам и действующим требованиям; provisional applicationId явно помечается тестовым. Release-подпись и обновление поверх предыдущего APK проверяются до распространения.

Web и Android версии развиваются отдельно. Изменение JSON не должно ломать установленный клиент; при невозможности обратной совместимости нужен явный план версии/обновления. Производственные миграции требуют копии и восстановления.
