# Docker / SQLite / Caddy на VDS

Адрес: https://139.100.205.135. Это ранняя версия: без email, с резервными кодами в коде 0.24, без автоматического назначения модераторов и подтверждённого нагрузочного испытания.

## Выпуск

`.github/workflows/vds-deploy.yml` работает только из main, вручную либо при изменении самого workflow. Обычный push кода не публикует его автоматически. Тесты выполняются до сборки; образ помечается SHA commit и передаётся на VDS через secret `vvd_ssh_wr`. Публичный ключ сервера закреплён, отключение проверки SSH не используется. Ключ не печатается и удаляется с runner после задания.

На VDS `/opt/wild-rift-community/releases/<SHA>` содержит образ и конфигурацию выпуска. `/opt/wild-rift-community/data` содержит SQLite, принадлежит UID 1000. Контейнер работает непривилегированным пользователем, без опубликованного порта приложения и с read-only файловой системой. База хранится в отдельном каталоге. Caddy использует существующие caddy_data/caddy_config volumes и публикует 80 TCP, 443 TCP/UDP.

PUBLIC_ORIGIN задаёт единственный разрешённый HTTPS origin. Host, Origin, маркер запросов и CSRF проверяются сервером; сеансы HttpOnly/SameSite=Strict/Secure. Caddy перезаписывает X-WR-Client-IP адресом соединения. Прямой доступ к приложению запрещается сетевой конфигурацией; не публиковать порт 3000. NODE_ENV=production требует PUBLIC_ORIGIN; локальный режим остаётся loopback HTTP.

## Копия и восстановление

Перед переключением сохраняются compose.yaml, Caddyfile и .env в backups/<дата>-<SHA>. Если приложение уже работало, оно останавливается, и весь data копируется в этот каталог. Каталоги backups доступны только root. Установщик 0.24 принимает схему 10, 11, 12, 13, 14, 15, 16, 17, 18 или 19. Перед миграцией к 19 включает ответ 503, сохраняет холодную копию, проверяет миграцию на отдельной временной копии и затем обновляет рабочую базу. SQLite содержит и изображения. Подробности — ACCOUNT_RECOVERY.md.

При ошибке до публикации установщик возвращает конфигурацию; после начавшейся миграции сохраняет failed-data и восстанавливает холодную копию. После открытия публичного трафика база автоматически не заменяется: это предотвращает удаление новых пользовательских записей. Холодную копию data восстанавливать при остановленном приложении по docs/BACKUP.md. Первое размещение без `DEMO_OWNER_HANDLE` создаёт новую пустую базу; с этой переменной и без маркера `demo-owner-assigned-v1` установщик останавливается до публикации, потому что передавать демо-клубы некому. Автоматическая внешняя резервная копия пока не настроена; копии на том же VDS не защищают от потери диска.

После успешного healthcheck установщик проверяет /api/me по HTTPS, записывает deployed-release и показывает контейнеры. Runner отдельно проверяет TLS без `-k`, гостевое API и HTML приложения. До включения стенда прежняя заглушка может кратковременно перезапуститься.

Модераторы задаются UUID через COMMUNITY_MODERATOR_IDS в серверном .env, согласно docs/MODERATION.md. Первая регистрация не получает административные права автоматически.


Установщик также сохраняет /opt/wild-rift-community/offsite-backup.sh с правами 700. Это только операторский инструмент: внешняя конфигурация и расписание не активируются автоматически. Инструкции — OFFSITE_BACKUP.md. Не считать выпуск подтверждением внешнего резервирования.
# Наполнение 0.26

Workflow задаёт `SEED_DEMO_COMMUNITY=1`. После холодной копии и до открытия трафика установщик атомарно добавляет явно отмеченные демонстрационные аккаунты/контент. Существующие записи не заменяются; схема остаётся 19. Успешное наполнение отмечается файлом `/opt/wild-rift-community/demo-seeded-v1`, последующие установки его пропускают. Ошибка до публикации восстанавливает холодную копию. После открытия трафика не заменять базу автоматически. Порядок и ограничения — [DEMO_COMMUNITY.md](DEMO_COMMUNITY.md).

В выпуске 0.27 флаг `SEED_DEMO_COMMUNITY` снят с workflow: существующее наполнение сохраняется, новое автоматически не создаётся. Установщик сохраняет прежнюю процедуру холодного резервирования, схема остаётся 19.

## Выпуск 0.28

Публикация выполняется после успешного полного Verify PR. Установщик принимает схемы 10–20, проверяет миграцию холодной копии и обновляет 19→20 под обслуживанием. Подробнее — AUDIT_FIXES_2026-10-04.md.

По прямому поручению владельца deploy передаёт шесть штатных демо-клубов аккаунту `lolokeksu` до открытия трафика. Проводится проверка на изолированной копии, затем операторская CLI с отдельным проверенным снимком. Снимок переносится в каталог текущей резервной копии. Ошибка до открытия трафика возвращает холодную базу. После успешной публикации маркер `demo-owner-assigned-v1` запрещает автоматическое повторное назначение следующих выпусков; read-only проверка владельца выполняется только в выпуске, который назначает владельца, до открытия трафика. Пока на сервере есть этот маркер, последующая передача клуба настоящим владельцем через интерфейс не останавливает следующие выкладки. Маркер хранится в `/opt/wild-rift-community`, а не в `data`: при переносе базы на новый сервер его нужно перенести вместе с данными, иначе изменённое владение остановит выпуск до публикации. Повторный seed не включается. Внешнее резервирование и расписания не активируются.
