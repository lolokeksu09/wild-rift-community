# Резервная копия и восстановление локальной версии

Текущая схема кода 0.24: 19. Здесь описана холодная копия SQLite: сервер должен быть полностью остановлен. Копирование только основного файла работающей WAL-базы может потерять подтверждённые записи. Горячее резервирование этим этапом не реализовано.

## Сохранение

1. Установить фактический путь COMMUNITY_DB (по умолчанию data/community.sqlite относительно каталога запуска).
2. Остановить сервер и дождаться завершения процесса. Исключить другие процессы, открывающие эту базу.
3. Скопировать весь каталог базы, включая существующие файлы -wal и -shm, в новый отдельный каталог. Не перезаписывать предыдущую копию.
4. Записать время копии, commit кода, версию Node и схему базы. Копия содержит приватные сообщения, хеши паролей и сеансы: ограничить доступ, не добавлять в Git или CI artifacts.
5. Запустить исходный сервер при необходимости.

## Проверка восстановления

Восстановление возвращает состояние на момент копии: поздние изменения отсутствуют, старые сеансы и права могут снова стать действительными. Не заменять рабочую базу для тренировки.

1. Скопировать резервный каталог в новый изолированный каталог восстановления, сохранив исходник и саму копию.
2. До запуска выполнить SQLite PRAGMA integrity_check (ожидается ok) и PRAGMA foreign_key_check (ожидается пустой результат). Проверить user_version=19.
3. Запустить соответствующий commit приложения с COMMUNITY_DB, указывающим на восстановленный файл, на свободном локальном порту. Не открывать доступ извне.
4. Проверить вход, сохранённые записи, запрет чужого доступа и создание новой записи. Убедиться, что исходник и резервная копия не изменились.
5. Для реального восстановления отдельно согласовать допустимую потерю поздних изменений и отзыв восстановленных сеансов. Не переносить старые -wal/-shm поверх другой базы.

## Автоматическая тренировка

`node --test server/tests/backup.test.mjs` создаёт только временные тестовые данные, останавливает сервер, копирует весь каталог дважды и открывает восстановленную копию. Проверяются целостность, внешние ключи, схема, аккаунт, сохранённый сеанс, новый вход, приватный пост, комментарий, запрет чужого доступа, новая запись и неизменность количества комментариев в исходнике и резервной копии.

Тест входит в npm test и npm run verify. Он не подтверждает сохранность внешнего хранилища, восстановление всех видов записей, восстановление повреждённой базы или время восстановления большой базы. Временные тестовые каталоги удаляются при завершении; рабочие данные не затрагиваются.


## Сеансы и резервные коды после ручного восстановления 0.24

Перед открытием восстановленной базы отозвать сеансы и старые коды одной транзакцией: BEGIN; DELETE FROM sessions; DELETE FROM recovery_codes; COMMIT;. Пароли вернутся к дате копии. Без этого использованные после копии коды и старые cookie могут снова работать. Зашифрованный restore из OFFSITE_BACKUP.md делает отзыв автоматически и не заменяет рабочую базу.
